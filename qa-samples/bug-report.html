PM-QA-001 (sample ID) · Bug · Performance

Idle pages spend about 400 ms of main-thread time per 10 s because the floating clock redraws on every frame

Status: Fixed and verified Severity: Medium (my assessment) Priority: Medium (my assessment) Reproducibility: Always, 3 of 3 runs
Project / component
Project Manager v2 / floating analogue clock (tickClocks() in web/assets/js/app.js, .clock__hand--s in web/assets/css/app.css)
Introduced
942fbf3, 28 Sep 2026 (“Add a floating analogue clock…”)
Fixed in
733b7e2, 1 Oct 2026
Affected build
942fbf3, the parent of the fix. The clock sits on every page, so every page is affected.
Environment
Re-measured on 28 Oct 2026: Windows 10 Home 10.0.19045, Playwright 1.63.0 with its bundled headless Chromium 153.0.8010.12, Node 24.15.0, page served by a static file server. The original ~320 ms figure comes from the commit message and test comment; the environment it was taken in is not recorded.
Preconditions
Build 942fbf3 served from v2/web on any static server. No database or sign-in is needed, because the sign-in page also shows the clock. Tab visible, no input during the measurement.

Steps to reproduce

  1. Serve the v2/web folder of commit 942fbf3, for example with npx http-server.
  2. Open /login.html in Chromium and wait until the .clock element is on screen.
  3. Open a DevTools Protocol session, enable the Performance domain and read the TaskDuration metric (call it t0).
  4. Leave the page completely idle for 10 seconds.
  5. Read TaskDuration again. The difference from t0 is the main-thread time the idle page used.

Expected result

A small decorative clock on an idle page costs almost nothing. The budget I later wrote into the regression test is under 64 ms per 10 s, which is 80% less than the ~320 ms first observed.

Actual result

The idle page used 382 to 417 ms of main-thread time in 10 s (about 4% of one core’s main thread), with nothing happening on screen but the clock. The commit and the spec comment both record ~320 ms for the original observation.

Evidence

The defect is invisible, so there is no screenshot; the numbers are the evidence. I re-ran the spec’s own method (same CDP metric, 10 s idle, login.html) against the parent build and the fixed build, 3 runs each, on 28 Oct 2026:

Main-thread time while idle, in ms per 10 s (lower is better)
BuildRun 1Run 2Run 3
942fbf3 (before the fix)417410382
733b7e2 (the fix)241815

Three different numbers appear on this page and they should not be mixed up: ~320 ms before and ~13 ms after are quoted from the fix commit’s message; 64 ms is the test’s pass threshold, not a measurement; the table is my own re-measurement. My measuring script was a one-off and is not in the repository.

What the old code did, from the diff of the introducing commit: tickClocks() rewrote the transform of three hands and the stroke-dasharray of the day ring, ran querySelectorAll, and then asked for the next frame:

function tickClocks() { /* set hand angles, day ring, aria-label */
    requestAnimationFrame(tickClocks);
}

Root cause

The second hand was driven from JavaScript so that it would sweep smoothly, and the loop ran once per screen frame (the browser’s display refresh rate) for as long as the page was visible. Almost all of that work was redundant: the hour and minute hands and the day ring change visibly only about once a minute.

Fix

733b7e2 moves the second hand into CSS and slows the JavaScript to once a minute:

  • .clock__hand--s now runs animation: clock-sweep 60s steps(480) infinite (8 steps a second), so it costs no JavaScript per frame.
  • tickClocks() sets a negative animation-delay so the sweep starts at the real second, then re-arms itself with setTimeout for the next minute boundary (+50 ms), and runs again when the tab becomes visible.

Trade-off I accepted: the second hand now moves in 8 steps a second rather than on every frame. The same commit also adds unrelated features (Mark complete, a service worker, analytics), so the clock change is only part of that diff.

Verification

  • Re-measured the fixed build 3 times: 24, 18 and 15 ms per 10 s, against 382 to 417 ms before (table above).
  • The fix commit’s message reports ~320 ms down to ~13 ms per 10 s on the author’s run.
  • Checked that the clock still works: the existing clock spec reads the real time, the day ring and the second hand’s angle (below).

Regression tests

  • tests/e2e/clock-cpu.spec.js: “an idle page with the clock does almost no main-thread work”. It loads login.html, idles 10 s and fails if the main thread was busy for 64 ms or more. It needs no database.
  • tests/e2e/interface.spec.js: “shows the real time on every page and the second hand keeps sweeping”. It guards against the cheaper clock being wrong or frozen: label, minute hand, day ring, and a second hand that is near the real second and then moves.

PM-QA-002 (sample ID) · Bug · UI

Progress bars never fill: the coloured bar has zero width at any percentage

Status: Fixed and verified Severity: Medium (my assessment) Priority: Medium (my assessment) Reproducibility: Always, per the fix commit
Project / component
Project Manager v2 / progress bar (.progress, .progress-bar in web/assets/css/app.css)
Introduced / fixed
Present from the v2 rebuild, eadb3c2 (26 Sep 2026, 16:29 +05:30). Fixed the same day in cedadfd (19:39 +05:30).
Environment
Chromium (the project’s Playwright browser), local Supabase stack with seed data. I did not re-run the old build for this report; the behaviour is taken from the commit message and the test it added.
Preconditions
Signed in as the seeded user developer@example.test, who is a member of projects whose progress is above 0%.

Steps to reproduce

  1. Open /dashboard.html.
  2. Find a project with a progress bar and a percentage above 0 (the bar has an accessible label such as “N% of tasks complete”).
  3. Compare the width of the coloured fill with the width of its track.

Expected result

The fill is as wide as its percentage of the track: 50% fills half of it.

Actual result

The fill has no width at any percentage, so every bar looks empty. The accessible label still announces the right percentage, so only sighted users lost the information.

Root cause

.progress and .progress-bar are <span> elements, which are inline by default and ignore width and height. The fill’s inline width: N% was therefore never applied. No test measured a bar’s rendered width before the fix.

Fix

cedadfd: display: block on both classes (2 lines of CSS).

Verification and regression test

tests/e2e/interface.spec.js: “progress bars fill to their percentage”. For every bar on the dashboard it computes fill width divided by track width and requires it to equal the percentage in the bar’s label, and requires at least one bar above 0% so the check cannot pass on empty data.
