Test plan: offline sync and roles

Project Manager v2 (Supabase + GitHub Pages, with a Tauri Windows shell). The feature area under test is the local copy with its outbox sync, and the four project roles that decide who may do what. This is a plan I wrote for my own project; entry and exit criteria are proposals for how I would run it, not a record of past releases.

Author: Apurv Das. Product: apurvdas.github.io/project-manager, branch v2-supabase. Related: test cases, bug reports.

1. Scope

  • Roles and permissions. Owner, manager, member and viewer inside a project, plus the site admin and non-members. Rules are enforced in Postgres (row-level security and functions); the UI only hides controls. Checked through the API as each seeded role and again in the browser.
  • Local copy and sync. The IndexedDB copy, sync_pull, live updates over Realtime, and wiping the copy on sign-out.
  • Offline editing. Edits queued in the outbox and sent in order with safe retries; the sync pill states (Synced, Offline, N waiting, Problem); creating things that depend on other unsaved things.
  • Conflict merge. Per-field merge when two people edit the same task or project; the newer edit wins on the same field and both sides are told.
  • Surfaces touched by the above. Kanban drag and drop, notifications, and layout at phone and desktop widths.

2. Out of scope

  • v1 (PHP / CodeIgniter) and the desktop-app installer, signing and auto-update. The desktop shell is covered only as far as its web code goes, with a stubbed Tauri bridge; smoke-testing the installed app is manual and separate.
  • Browsers other than Chromium. The Playwright project is Chromium only.
  • Load and stress testing, and performance beyond the idle-CPU guard.
  • Security testing beyond the permission rules above (no penetration test), and a full accessibility audit.
  • Supabase itself, and email delivery for sign-in links and password reset.

3. Approach

LevelWhat it coversHow
API permission testsEvery role’s rights, merge rules, retry safety, sync cursors, notification accesstests/rls.test.mjs, run with npm test (Node’s test runner and supabase-js). It resets the database, signs in as each seeded user and calls the API exactly as a browser would, checking for the Postgres permission error 42501 where a role must be refused.
Playwright E2EUser journeys: board, offline round trips, conflicts, live updates, notifications, layoutSpecs in tests/e2e/, run with npm run e2e. Two browser contexts stand in for two people; context.setOffline() stands in for losing the network. A helper truncates and re-seeds the database before each test.
Manual and exploratoryWhat the scripts do not assert: wrong-password message, sign-in as the next person after sign-out, 375 px layout, touch behaviour, the installed desktop appCharters from the test-case table; findings go in as bug reports in the style of these samples.
Layout scriptsHorizontal overflow, header controls and the clock on screen across 20 viewport sizes on 5 pages (sweep) and 12 pages at phone width (audit)tests/viewport-sweep.mjs and tests/mobile-audit.mjs, run by hand (not part of npm run e2e).

Each defect found becomes a regression test at the lowest level that can catch it (the idle-CPU and progress-bar bugs in the bug report samples both did).

5. Test data

  • The seed file creates users admin, manager, developer, designer, tester and a site admin IronWarrior, each with a local-only password from the seed file.
  • In project Website Redesign: admin is owner, manager is manager, designer and developer are members, tester is a viewer. Internal Wiki has admin as owner and developer as member; designer is not in it, which makes it the non-member case.
  • Seeded tasks sit in four columns (todo, in_progress, review, completed). Every test resets to this state, so ids and names are stable.
  • Two-person cases use two separate browser contexts, never two tabs of one session.

6. Entry and exit criteria

Entry (proposed)Exit (proposed)
  • Build deployed to the local stack from a clean supabase db reset.
  • Migrations applied and seed data loaded.
  • Smoke path works by hand: sign in, open a project, open the board.
  • Test cases for the changed area reviewed.
  • All P1 cases pass; no open Critical or High defect.
  • API permission suite and E2E suite green on a fresh reset.
  • Every P2 failure has a ticket and a decision (fix or accept).
  • Manual cases for the area run on the final build.
  • Layout scripts report no overflow.

7. Risks and mitigations

RiskMitigation
Automated runs wipe the shared local database, which logs out and clears whatever I was doing by hand.Run suites on the local stack only, one worker (the config sets workers: 1), and sign in again afterwards.
Live updates can be dropped just after a database reset, which makes tests flaky.The liveReady helper proves the channel with a harmless change before the timed step.
Conflict resolution depends on edit timestamps, so two edits made in the same second are ambiguous.Conflict tests separate the two edits by 1.1 s.
Offline behaviour needs the service worker, which only registers on a stamped build.Offline specs run against the stamped server on port 8124.
No CI job runs the tests. The repository’s workflows only deploy the site and build the desktop app.Run both suites before each release; adding them to a pipeline is a follow-up.
The free Supabase tier pauses after about a week idle and rate-limits email.Resume the project before a production smoke check; use Mailpit locally.
Chromium-only automation hides issues in other engines.Manual pass in Firefox and on a phone for layout and touch before release.
