Case study

Problem

WreckBox keeps a DJ's music in one library, works out BPM, key and energy for every track and tags the files. It is an app by another developer (moloyb301-eng); this is my native rewrite of it, aimed at old, cheap Windows PCs.

Limits

Weak hardware, a 300 ms first-paint budget, and no frame loop, so nothing runs when nothing changes.

What I built

  • One native executable (Win32, Direct2D).
  • Ported the Rust audio-analysis engine (tempo, key, energy) to C++ with my own SSE2 FFT, computed frame by frame so a 5-minute track needs no spectrogram in memory. Results match the Rust engine on every file both can read.
  • Low-latency playback: libVLC into a 0.25 s ring, miniaudio / WASAPI at 20 ms periods, and a sample-accurate "heard" clock that keeps visuals on the beat, with automatic Bluetooth latency compensation.
  • The Soulseek peer-to-peer protocol, natively (server, peers, relayed transfers), with 28 messages verified byte for byte against a reference implementation.

Numbers

  • First paint in 105–147 ms against a 300 ms budget; search across 5,000 tracks in 0.8 ms.
  • 0% idle CPU and about 43 MB of RAM at rest.
  • Memory after scrolling roughly halved (about 92 to 50 MB) by fixing GPU brush retention and moving to the Windows segment heap.

Testing

  • 12 CTest suites (690+ assertions); CI builds, tests, smoke-tests and packages each release.
  • Smoke testing caught a crash on every app exit (2 root causes fixed).
  • Compatibility testing of 18 audio formats found 3 audio defects, each locked in with a regression test.

Case study

Problem

Most visualizers only react to the sound that is playing. DasVis maps the song first, so the visuals can anticipate build-ups and drops.

Limits

Runs on GPUs back to Direct3D 11 feature level 10_0 (about 2008 hardware), pixel shaders only. Big flashes are held to 3 a second.

What I built

  • Streaming song analysis (STFT, harmonic-percussive separation, dynamic-programming beat tracking, novelty-based section detection) maps beats, build-ups and drops in about 4–6 s using about 6 MB.
  • 15 GPU scenes, including stable-fluids, reaction-diffusion and a one-million-star galaxy, all as pixel shaders on ping-pong textures.
  • Quality tier and render scale chosen from GPU timestamp queries.
  • Frame-exact H.264 video export through Media Foundation, Spout GPU texture sharing, and WLED LED-strip control over realtime UDP.

Numbers

  • About 5% of one CPU core and +20 MB of RAM at the low tier.
  • Song map in about 4–6 s using about 6 MB.

Testing

  • Automated GPU rendering tests on a software renderer (WARP).
  • Determinism tests: same input, bit-identical frames.
  • A photosensitivity (accessibility) test for the flash limiter.

Case study

Problem

Course project for AI Powered Cybersecurity Network Architecture and Threat Mitigation (MCA): find how risky a home network is, and notice when it changes. The screenshots use sample data.

Limits

A 4 GB laptop, unattended, standard library only. Alerts only: it never changes the network, pins the home network on first run and skips any other network.

What I built

  • Finds every device on the subnet and scans the top 200 TCP ports with versions, plus a UDP probe for SNMP and UPnP, every 6 hours.
  • Scores each finding by likelihood × impact into device and network risk (Low to Critical).
  • An anomaly model learns how often each port is open on each device and flags scans far more surprising than that device's history (it starts after 20 scans).
  • A SQLite history (new devices, newly opened ports), a self-contained HTML report with fix steps, and a Windows notification only for High / Critical or unusual findings.

Numbers

  • Top 200 TCP ports, every 6 hours, on a 4 GB laptop.

Testing

  • 44 unit tests with mocks.
